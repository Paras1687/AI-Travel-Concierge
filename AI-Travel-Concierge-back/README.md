# TripWeave Backend

The TripWeave backend provides the API and workflow layer for the TripWeave travel planning application. It handles user input, validates required trip information, coordinates external travel services, retrieves weather and accommodation data, and generates the final itinerary using a LangGraph-based workflow and Google Gemini.

## Overview

The backend is responsible for coordinating the complete travel-planning process.

The general flow is:

```text
Frontend Request
       |
       v
     FastAPI
       |
       v
Trip Information Processing
       |
       v
Required Information Check
       |
       +---- Starting Point Available
       |             |
       |             +---- Missing -> Request from User
       |
       +---- Budget Available
       |             |
       |             +---- Missing -> Request from User
       |
       v
External Data Collection
       |
       +---- Flights
       +---- Other Transportation
       +---- Hotels
       +---- Weather
       |
       v
LangGraph Workflow
       |
       v
Gemini
       |
       v
Itinerary Generation
       |
       v
Structured Response
       |
       v
Frontend
```

The workflow is designed to collect the required constraints before generating the itinerary.

## FastAPI

FastAPI acts as the HTTP layer between the frontend and the backend workflow.

Its responsibilities include:

1. Receiving requests from the frontend.
2. Validating request data.
3. Starting the travel-planning workflow.
4. Returning the workflow response.

The API can also provide interactive documentation through FastAPI's standard documentation endpoints when the development server is running.

## LangGraph Workflow

LangGraph is used to coordinate the different stages of the travel-planning process.

Instead of handling the entire request through one LLM call, the backend separates the process into logical stages.

A simplified representation is:

```text
Input
  |
  v
Information Extraction
  |
  v
Required Information Validation
  |
  +---- Missing Information
  |          |
  |          v
  |      User Input
  |          |
  +----------+
  |
  v
Travel Information
  |
  +---- Flights
  +---- Transportation
  +---- Hotels
  +---- Weather
  |
  v
Itinerary Generation
  |
  v
Final Response
```

Each node is responsible for a specific part of the workflow.

This separation makes it possible to modify individual parts of the system without rewriting the complete travel-planning process.

## State Management

The workflow maintains a shared state containing the information required by different nodes.

Depending on the current implementation, the state can contain information such as:

```text
User Prompt
Destination
Starting Point
Start Date
End Date
Trip Duration
Budget
Travel Preferences
Flight Information
Transportation Information
Hotel Information
Weather Information
Generated Itinerary
```

The state allows information generated by one node to be used by subsequent nodes.

For example:

```text
Prompt
  |
  v
Destination extracted
  |
  v
Destination stored in state
  |
  v
Hotel node reads destination
  |
  v
Hotel information added to state
  |
  v

```

## User Input Handling

The backend does not assume that all required information will be available in the initial prompt.

### Starting Point

The workflow checks whether a starting point has been provided.

If it is available, it is used directly.

If it is missing, the application requests the starting point before continuing.

### Budget

The same approach is used for the travel budget.

If a budget is provided, it is stored and used during planning.

If it is missing, the workflow requests it before continuing.

## Date Handling

The frontend provides the starting and ending dates through the calendar interface.

The backend uses these dates to determine the trip duration.

```text
Start Date
     +
End Date
     |
     v
Trip Duration
     |
     v
Itinerary Planning
```

The backend should treat the selected dates as explicit user input rather than relying on an LLM to infer the duration from natural-language text.

## Transportation Integration

The backend integrates transportation information into the travel-planning workflow.

Transportation-related data can include:

- Flights
- Trains
- Buses
- Other available modes of transportation

Flight information is processed separately where required, while the overall transportation information is made available to the frontend through the backend response.

The transportation data can also be used as an input to itinerary generation.

## Hotel Integration

The backend retrieves hotel information based on the destination and relevant trip parameters.

The resulting hotel options are stored as part of the workflow state and returned to the frontend.

Hotel information can include details such as:

- Hotel name
- Location
- Pricing information
- Rating
- Other available metadata

The exact fields depend on the external hotel service being used.

## Weather Integration

Weather information is retrieved for the destination and relevant travel period.

The weather data is made available to the itinerary-generation workflow so that the generated plan can account for expected conditions.

For example, weather information can influence the suitability of outdoor activities.

## Gemini Integration

Google Gemini is used for the language-processing and itinerary-generation components of the backend.

Gemini can be used to:

- Process natural-language travel requests
- Extract trip requirements
- Interpret user preferences
- Generate structured itinerary content
- Combine collected travel information into a final travel plan

External APIs provide factual travel information, while Gemini is responsible for language understanding and generation.

This separation reduces the need for the LLM to invent information that can instead be retrieved from external services.

## Itinerary Generation

The final itinerary is generated after the required information and relevant external data have been collected.

The generation process can consider:

```text
Destination
Start Date
End Date
Trip Duration

Budget
User Preferences

Hotels
Weather
       |
       v

       |
       v
```

The itinerary is returned as part of the final backend response and displayed by the frontend.

## Error Handling

The backend should handle failures from individual services without causing unnecessary failures in the complete workflow.

Potential failure cases include:

- Invalid user input
- Missing required information
- Invalid API credentials
- External API failures
- No available transportation options
- No available hotels
- Weather API failure
- Gemini service unavailability
- Invalid or incomplete API responses

External API calls should be validated before their results are passed to subsequent workflow nodes.

## Development Guidelines

When modifying the backend:

1. Keep workflow nodes focused on a single responsibility.
2. Avoid placing large amounts of workflow logic directly inside FastAPI routes.
3. Keep API credentials in environment variables.
4. Validate external API responses.
5. Keep state definitions synchronized with workflow requirements.
6. Avoid unnecessary changes to unrelated workflow components.
7. Test individual nodes before testing the complete workflow.
8. Keep frontend-specific logic outside the backend.

## Troubleshooting

### Gemini Service Unavailable

If Gemini returns a temporary service-unavailable response, retry the request after a short interval and verify that the configured model and API credentials are correct.

### External API Failure

Check:

- API credentials
- Request parameters
- API limits
- Network connectivity
- Response structure

### Workflow Failure

When a LangGraph workflow fails, inspect the state passed between nodes and identify the node at which the failure occurs.

Particular attention should be given to:

- Missing state fields
- Incorrect field names
- Unexpected API response formats
- Incorrect conditional transitions
- Invalid LLM output
